# Sales System

B2B-система управления онлайн заказами компании по производству и продаже строительных материалов.
Микросервисная архитектура: приём заказов, резервирование товаров на складе, оплата.

## Статус

 В разработке. Готовы order-service, product-service и payment-service


 | Сервис | Назначение | Статус |
 |--------|-----------|:------:|
 | order-service | Заказы, статусы, оркестрация Saga | ✅ базовый функционал |
 | product-service | Товары, резервирование склада | ✅ базовый функционал |
 | payment-service | Оплата, возврат средств | ✅ базовый функционал |
 | analytics-service | Отчёты по продажам | ⬜ планируется |

## Стек

Java 25, Spring Boot 4.1, PostgreSQL 16, Liquibase, Docker, Maven, Resilience4j, JUnit 5 + Mockito, Testcontainers, springdoc-openapi

## Быстрый старт

Требования: Docker, JDK 25

```bash
# поднять базы данных
docker-compose up -d

# запустить сервисы (каждый в своём терминале)
cd order-service && ./mvnw spring-boot:run
cd product-service && ./mvnw spring-boot:run
cd payment-service && ./mvnw spring-boot:run
```

order-service: http://localhost:8081 (Swagger: /swagger-ui.html)
product-service: http://localhost:8082 (Swagger: /swagger-ui.html)
payment-service: http://localhost:8083 (Swagger: /swagger-ui.html)

## Сценарий заказа

1. **Создание** — `POST /orders`: проверка наличия и резервирование товара по всем позициям.
   Заказ атомарен: если хотя бы одной позиции не хватает, резервы откатываются и заказ не создаётся.
   При успехе заказ получает статус `CREATED`, товар резервируется на 48 часов.

2. **Оплата** — `POST /orders/{id}/pay`: отдельная операция. При отказе (например, недостаточно
   средств) заказ **остаётся** в `CREATED` — клиент может пополнить счёт и повторить оплату,
   не оформляя заказ заново. При успехе — `PAID`.

3. **Истечение резерва** — если заказ не оплачен за 48 часов, фоновая задача освобождает
   товар и переводит заказ в `CANCELLED`.

Состояния: `CREATED → PAID` или `CREATED → CANCELLED`.


## Ключевые решения

**Monorepo** - все сервисы в одном репозитории. Один разработчик, проще менять контракты между сервисами и показывать систему целиком. В команде с отдельным владением сервисами выбрал бы multi-repo.

**Database per service** - у каждого сервиса своя БД, порты разведены. Сервисы не обращаются к чужим данным напрямую, только через API - это сохраняет независимость сервисов.

**Liquibase + `ddl-auto: validate`** - схемой управляют миграции, Hibernate только проверяет соответствие. Схема воспроизводима и версионирована.

**`@EntityGraph` вместо `JOIN FETCH` при пагинации** - `JOIN FETCH` размножает строки при джойне коллекции, из-за чего `LIMIT` применяется в памяти. `@EntityGraph` позволяет отобрать страницу на уровне БД, а затем подтянуть связи.

**DTO на границах** - сущности не выходят наружу. Клиент не задаёт цену, сумму, статус и даты — их проставляет сервер.

**Единый формат ошибок** - `@RestControllerAdvice` возвращает предсказуемую структуру с корректными кодами (404 для отсутствующего заказа, 400 для невалидных данных). Детали внутренних ошибок не раскрываются клиенту, логируются на сервере.

**Стабильная сериализация страниц** - `PageSerializationMode.VIA_DTO`, чтобы формат ответа не зависел от внутренней структуры Spring Data.

**Атомарный UPDATE для резервирования склада** — проверка остатка и списание выполняются одним запросом (`UPDATE ... WHERE quantity_available >= :qty`), поэтому гонка между параллельными заказами невозможна. Пессимистичную блокировку не использовал: она удерживает замок на всю транзакцию и создаёт риск deadlock при резерве нескольких позиций. Оптимистичная не подходит из-за частых конфликтов на популярных товарах — пошли бы холостые повторы.

**Обработка отказов межсервисных вызовов** — HTTP-коды чужого сервиса транслируются в доменные исключения в слое клиента: 404 → товар недоступен, 409 → недостаточно остатка, сетевой сбой → сервис недоступен. Наружу отдаются осмысленные коды (404/409/503), а не общий 500.

**Таймауты** — connect 2s, read 5s. Без них зависший сервис-сосед забивает пул потоков и роняет вызывающий сервис (каскадный отказ).

**Circuit Breaker (Resilience4j)** — размыкается при 50% неудач в окне из 10 вызовов, 30 секунд в открытом состоянии, 3 пробных вызова в half-open. Бизнес-исключения (нехватка товара, отсутствие товара) исключены из подсчёта: это корректные ответы сервиса, а не его сбой. Состояние наблюдаемо через `/actuator/circuitbreakers`.

**Correlation ID** — сквозной идентификатор запроса. Фильтр на входе берёт его из заголовка или генерирует, кладёт в MDC; интерцептор RestClient прокидывает дальше в исходящих вызовах. По одному ID собирается весь путь запроса через все сервисы.

**Saga с компенсирующими транзакциями** — оформление заказа затрагивает три сервиса с независимыми БД, где `@Transactional` не работает. Каждый успешный шаг запоминается; при сбое выполняется откат в обратном порядке: возврат платежа, освобождение резерва, отмена заказа. Ошибка компенсации логируется с пометкой о необходимости вмешательства, но не прерывает откат остальных шагов и не затмевает исходную причину сбоя — клиент получает настоящую причину, а не «не удался откат».

**Идемпотентность компенсаций** — повторный возврат платежа не падает, а возвращает то же состояние; возврат неудавшегося платежа корректно ничего не делает. Освобождение резерва защищено условием `quantity_reserved >= :qty` — повторная компенсация не уводит остаток в минус.

**Оплата отделена от создания заказа** — отказ платежа не откатывает заказ. Для B2B это принципиально: клиент, у которого не хватило средств, пополняет счёт и оплачивает тот же заказ, а не вводит двадцать позиций заново. Технический сбой (сервис недоступен) и нехватка товара по-прежнему приводят к откату — это разные по природе ситуации.

**Защита scheduler от двойной обработки** — в production сервис работает в нескольких экземплярах, и фоновая задача запускается в каждом. Захват заказа реализован атомарным UPDATE `WHERE id = ? AND status = 'CREATED'`: кто первый сменил статус, тот и освобождает товар, остальные получают 0 изменённых строк и пропускают запись. Захват выполняется до обращения к product-service — иначе в момент гонки товар освободился бы дважды. Distributed lock через Redis рассматривался, но добавляет точку отказа и требует управления TTL, не отменяя необходимости идемпотентности.

**Транзакция не удерживается во время внешних вызовов** — работа с БД (`tryCancelExpiredOrder`) и HTTP-вызовы (`releaseReservations`) разнесены по разным методам разных бинов: транзакция закрывается до похода в сеть. Разные бины нужны из-за self-invocation — вызов `@Transactional`-метода изнутри того же класса идёт мимо прокси.
